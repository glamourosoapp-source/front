# Front — Dashboard del CRM Glamouroso

Next.js (App Router) + React + TypeScript + MUI + Zustand. Habla con el Back (`localhost:3002/api`) y corre en `localhost:3000`. Mapa general: [../AGENTS.md](../AGENTS.md), reglas de frontend: [../docs/FRONTEND.md](../docs/FRONTEND.md).

## Comandos

```bash
bun run dev      # next dev --turbopack en :3000
bun run build    # build de producción — ver PELIGRO abajo
bun run lint
cd shared && bunx tsc --noEmit
```

## PELIGRO: build vs dev server

**No correr `bun run build` mientras el dev server está activo**: comparten `.next` y el build de producción deja el dev server tirando 500 hasta regenerar `.next`. Verificar antes con `lsof -iTCP:3000 -sTCP:LISTEN`; si está corriendo, avisar o usar un worktree.

## Reglas

- `shared/` es copia duplicada del contrato con `Back/shared/`. **Mantener ambas en sync** en el mismo cambio.
- **El layout raíz tiene que envolver todo en `AppRouterCacheProvider`** (`@mui/material-nextjs/v15-appRouter`, en `src/app/layout.tsx`). Es lo que conecta el cache de emotion con `useServerInsertedHTML` de Next. Sin eso, el SSR emite el `<style data-emotion>` de `CssBaseline` **dentro del `<body>`**, justo antes del contenido, y en el cliente emotion lo reinyecta en el `<head>`: React encuentra `<main>` donde esperaba `<style>` y tira "Hydration failed" en **todas** las rutas, `/login` incluido. Se recupera renderizando en cliente, pero ensucia la consola y parpadea la caja del POS. Si alguien saca el provider, vuelve el bug.
- Permisos en UI: `usePermissions()` (`src/lib/permissions.ts`); el sidebar filtra por módulo y los botones se gatean por acción. Rol admin = bypass. En pedidos, **borradores van por `orderDrafts`, no por `orders`**: la pestaña Borradores y su badge por `orderDrafts:view`, "Guardar borrador" por `create`, editar/eliminar la fila draft por `update`/`delete` (`canEditRow`/`canDeleteRow` de `DataTable`) y "Convertir en pedido" por `orderDrafts:update` + `orders:create`.
- **Punto de venta**: la administración vive en `/dashboard/pos/*` (sección "Punto de venta" del sidebar, gateada por `posBranches`/`posInventory`/`posReports`/`posRestock`). Las pantallas de operación (`/pos` caja, `/fabrica`, `/franquicia`) van **fuera** de `src/app/dashboard/` para no heredar sidebar ni topbar, como `/login`. Tras iniciar sesión, `landingRouteFor` (`src/lib/permissions.ts`) decide el destino: cajero a `/pos`, fábrica a `/fabrica`, franquicia a `/franquicia`, el resto a `/dashboard`. Solo se agregan al sidebar rutas que ya existen. En la caja, la columna **Existencia** y `F3` piden `posInventory:view`, y `F4` Ventas del día pide `posReports:view`: el perfil Cajero no los tiene, así que no se pintan (el `colSpan` de la fila vacía también depende de ello) y el Back tampoco manda la existencia.
- **La caja como app del escritorio**: `src/app/manifest.ts` + `public/icons/*` (generados con `bun run icons:pos` desde `src/app/icon.svg`; el script también copia el `.ico` a `PrintAgent/installer/`). Tres trampas ya pagadas: (1) Chrome **no instala** una PWA con iconos solo SVG y descarta los que declaran un `sizes` distinto al real —por eso los PNG están versionados y el script los mide—; (2) `metadata.icons` del layout raíz **se ignora** porque existe `app/icon.svg`: las convenciones de archivo ganan, así que el icono de Apple es `app/apple-icon.png`; (3) `src/app/pos/layout.tsx` es de **servidor** solo para exportar `metadata.title` (el título es lo que Windows muestra en la barra de tareas de la app instalada) y toda la lógica de cliente vive en `pos/PosShell.tsx`. El evento `beforeinstallprompt` se captura en el layout vía `src/lib/pwa-install.ts` —Chrome lo dispara una vez y temprano, y las pantallas del POS se navegan sin recargar—; en desarrollo nunca llega porque el SW no se registra. Funciona igual en Windows y en Mac; `installTarget()` decide si la copia dice "escritorio" o "Dock", y se resuelve en el efecto del hook, no en el render, para no romper la hidratación.
- **Portal de franquicias** (`/franquicia`): está hecho para pedidos de decenas de partidas, no de tres. El catálogo se trae completo (`limit=1000`, ~850 renglones) y se filtra en el cliente; la cantidad se edita desde la fila del catálogo con el mismo `Stepper` que el carrito; el pedido a medio armar se guarda en `localStorage["franquicia.pedido.v1"]`; y "Repetir el último pedido" lo reconstruye contra el catálogo vigente. Dos trampas que ya costaron: `Stepper` vive **fuera** del componente de página (declarado adentro, React lo trata como un tipo nuevo en cada render y el `<input>` pierde el foco a la primera tecla), y el carrito guardado se lee en un efecto, no en el `useState` inicial, para que el primer render del cliente coincida con el del servidor. Por debajo de 1040 px el carrito deja de ser columna y pasa a ser **hoja inferior + barra fija** (`.fr-bar` / `.fr-cart.is-open` en `franquicia.css`): apilar sin más dejaba el pedido después de 60 renglones de catálogo. Ahí los tamaños táctiles van al final del archivo (misma especificidad que las reglas base: gana la última) y la hoja lleva `top: auto` para no heredar el `top: 20px` del escritorio. Detalle: `docs/product-specs/franquicias-portal.md`.
- **Service worker del POS**: se registra **solo en producción** (`src/app/pos/layout.tsx`, `fabrica/layout.tsx`). En desarrollo cacheaba el app shell y servía la caja vieja después de cada edición, con la CSS y el JS anteriores; si aparece código viejo en `/pos`, desregistrar el SW y borrar `caches` en las devtools.
- Moneda y cantidades: `src/lib/format-money.ts` (`formatMoney`, `formatMoneyShort`, `formatQuantity`). Es el punto único; antes estaba duplicado en el Overview, el diálogo de top productos y las dos gráficas.
- Fechas DATEONLY (`YYYY-MM-DD`): nunca `new Date("YYYY-MM-DD")` para mostrar (corre el día por timezone) — usar `src/lib/format-date-only.ts`.
- Etiqueta "Creado por" en pedidos: `orderCreatorLabel` en `src/constants/orders.ts` (`source='whatsapp'` → "Agente IA").
- **Seguimiento de clientes** (`/dashboard/seguimiento`, módulo `customerFollowup`): tarjetas/chips por cubo 15/30/60 y botones WhatsApp/Llamar que abren `wa.me` y `tel:` con el teléfono del **vendedor**, no el número de la empresa (`src/utils/contact-links.ts`; no pasan por el guardián ni gastan cupo). La columna y el selector de vendedor se renderizan para admin o alcance `team` del perfil (`getCustomerFollowupScope`); las opciones salen de `summary.sellers`, no de `/users`. El server pinza a cada quien a su alcance.
- Impresión: clases `.print-only` + `@media print` en `globals.css`; exports Excel/PDF paginan de a 200. La hoja imprimible **debe montarse por portal como hijo directo de `<body>`** (ver `OrderPrintSheet`): el `@media print` saca del flujo todo lo demás con `body > *:not(.print-only) { display: none }`; si se anida en el layout, el alto del dashboard vuelve a generar una página en blanco. Para varias notas de golpe está `OrdersPrintSheets` (un solo `.print-only` con una nota por hijo y `breakAfter: page` salvo la última), que usa el botón "Imprimir pedidos" del listado (permiso `orderPrint`).
- **Vista previa de la nota**: `OrderNotePreviewDialog` monta el MISMO `OrderNote` en pantalla (hoja carta de 816px escalada con `transform` para caber en el diálogo) y lo baja como PNG con `src/lib/node-to-image.ts` (DOM → `<foreignObject>` → canvas, sin dependencias). **No llama a `POST /orders/print`**: no marca `printedAt` ni pinta la fila. Tres cuidados: (1) el clon se pinta SIN las hojas de estilo de la app, así que `node-to-image` copia los estilos calculados nodo por nodo (`COPIED_PROPERTIES`) — sin eso `box-sizing` volvía a `content-box` y la imagen salía cortada 48px de la derecha, y el reparto de columnas cambiaba; (2) el SVG se arma con `XMLSerializer` sobre nodos reales, nunca concatenando strings: una comilla de `font-family` rompe el XML y la imagen no se genera; (3) las medidas del diálogo se toman con callback refs, no con `useEffect`, porque el `Dialog` de MUI monta su contenido después del primer commit.
- **Impresión de notas**: imprimir (listado o detalle) pasa por `POST /orders/print`, que marca `printedAt`/`printedBy` **solo la primera vez**; el listado pinta esas filas de azul (`isRowHighlighted` de `DataTable`) y el detalle cambia el botón a "Reimprimir". Reimprimir está permitido para cualquiera con el permiso `orderPrint`: la marca azul indica "esta nota ya salió alguna vez", con la fecha y el usuario de la primera impresión.
- **`node_modules/@glamouroso/shared` es una COPIA, no un symlink**: tras tocar `shared/src` hay que correr `bun install` en `Front/` (y en `Back/`) o el cambio no llega ni al dev server ni al build.
